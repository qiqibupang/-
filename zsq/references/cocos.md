# Cocos 脚本与预制体规范

只要当前项目是 Cocos 项目，本章就适用于所有新增和修改的脚本与预制体，与是否为试玩广告任务无关：

- 脚本组件能放在预制体父节点时，统一挂在父节点。父节点只承担预制体身份、脚本和整体变换，不放 Sprite、Label、碰撞体、刚体等表现或物理组件。
- Sprite、Label、RigidBody2D、Collider2D 以及其他表现和物理组件统一放在父节点的子节点下；子节点按职责命名。脚本已挂在预制体根节点时，控制整体对象直接使用 `this.node`，不再暴露指向自身的根节点引用；只有控制目标确实不同且无法唯一确定时，才显式绑定目标。
- 只实现需求所需的逻辑、变量和分支，不为假想扩展新增无实际用途的状态、开关、包装层或兼容逻辑。Inspector 只暴露需要用户调参、选择资源或明确指定对象的必要属性；运行时状态、临时变量、可推导值，以及能从自身或已绑定组件唯一确定的引用，不加 `@property`。
- 同一配置只保留一个来源；原生组件或已有引用已能提供的信息，不再新增重复字段要求用户配置。多个资源或组件承担不同职责、无法唯一确定目标时，保留必要的显式绑定，不靠硬编码名称或随意取第一个对象来减少字段。具体实现依据当前项目的职责划分与使用方式决定，不将单个项目的实现固化为通用规则。
- 清理前区分重复／废弃配置与用户明确保留的功能入口。暂未赋值、资源尚未制作或当前场景未使用，不代表无用；用户明确要求预留的配置和扩展入口应保留。删除确认冗余的字段时，同步清理预制体、场景及实例覆盖中的旧数据，并验证相关行为，不能只隐藏 Inspector 字段。
- 暴露引用是预制体契约，不写“缺失时改用脚本节点”“缺失时跳过”“缺失时创建默认对象”等兜底游戏逻辑。必填引用直接使用；预制体和场景交付前检查引用完整。运行时对象已经销毁、停用等状态判断属于正常生命周期处理，可以保留。
- 所有对编辑器暴露的属性使用中文 displayName；脚本类使用中文 @ccclass(中文脚本名)，让组件和属性在编辑器中显示中文。代码内部标识符按项目既有命名保持一致，不能用内部英文名代替外部显示名。
- 预制体结构、脚本挂载位置、子节点职责和必填引用在交付时一起校验；发现父节点存在 Sprite、Label 或碰撞体时，优先调整预制体结构，不在脚本里增加兼容分支。

# 试玩广告任务

## 触发判断

- 用户提到构建、打包、出包、压缩包体等任务时，先判断当前项目是否为 Cocos（看项目根目录是否有 `package.json` 里的 `creator` 字段、`assets/`、`settings/`、`extensions/super-html` 等）。
- 是 Cocos 项目且用户未明确说明是否为试玩广告时，一次性问两件事再动手：本次是否是试玩广告打包任务；如果是，本次打包名称是什么。两个问题合在一条消息里问，不分两轮。用户已经明确说了其中一项就只问剩下那项，都说了就不问。
- 确认是试玩打包后，本章全部小节启用，后续「继续构建」「继续优化」等指令直接适用，不重复问。用户回答不是试玩任务，或项目不是 Cocos，则按普通构建任务处理，只用上方「通用协作偏好」。
- 本章的验收要求优先于「验证与完成标准」里的"聚焦验证"，但不扩展无关检查。

## 命名与默认渠道

- 打包名称按上方「触发判断」在开工前问清；不沿用上次名称或项目目录名代替。
- 默认渠道 `google、applovin、facebook、moloco、tiktok`；用户指定范围时以其为准，项目旧配置里的其他渠道不自动加入。
- 所有渠道同一命名规则：以用户给的名称为模板，只替换其中的渠道字段为"渠道名 + 渠道"，其余保留；渠道名大小写沿用项目或打包工具的写法，不从示例推导。HTML 加 `.html`，ZIP 内的 HTML 同样按渠道命名。
- 用户给完整路径时只替换末尾名称中的渠道字段，父目录不变。示例（仅示意，不是固定名称或上传授权）：
  `\\172.16.0.88\全球g2\UE组\2026\试玩AD\一秒八刀\试玩广告-260908-位面2欧美-google渠道-打墙击飞绿草地-内部UE-一秒八刀-mjw-zsq`
  对应 facebook 为 `试玩广告-260908-位面2欧美-facebook渠道-打墙击飞绿草地-内部UE-一秒八刀-mjw-zsq`。

## 体积红线

- Google 渠道压缩包解压后的全部文件总字节数（单 HTML 结构时即该 HTML 的字节数）**≤ 5,000,000 B** 即达标，不要求额外余量；超过则继续优化。
- 按十进制字节比较，不能用 ZIP 压缩后大小代替解压后大小。报告时给实际字节数和距 5,000,000 B 的剩余/超出字节数。
- 这是 Google 渠道的验收标准，不是构建范围限制：其他渠道仍按项目配置正常生成，不因 Google 超限而只构建 Google 或删除其他渠道产物。

## Cocos 构建与优化落层

- 构建与压缩不得删减任何已经使用的内容或功能，包括人物、骨骼、动画片段及动作状态、特效、音频、贴图、场景和交互逻辑。人物原有动画必须保留并正常播放，不得通过删除动画、停用功能、移除运行时所需资源或排除出包来达成体积目标；只能在保留原有内容、功能和表现的前提下优化存储、编码、压缩及资源复用。
- 清理资源前必须确认其确实未被使用，同时检查场景、预制体、材质、动画、代码及动态加载路径；静态引用未检出、当前关卡未出现或文件名含 `_备份` 都不能作为删除依据。用途不确定就保留。优化后针对受影响内容验证其仍可加载、播放和触发，不能用包体达标代替内容完整性验收。
- 项目使用 SuperHTML 扩展时，以扩展实际打包规则和文件结构为准。Google 采用单 HTML 还是多文件 ZIP，沿用项目当前 SuperHTML 配置和渠道现行规则，不自行切换结构、不拆分或外链资源。
- 超限时进入"统计体积来源 → 优化 → 重新构建 → 解压测量"迭代，依据每轮实际字节数决定下一步，直到达标；不停在一次尝试，无收益的方案及时更换。优化须保留玩法、必要内容和商店跳转，不能靠删验收要求凑体积。
- 优化优先落到源工程或 Cocos 构建配置：`assets/` 源图转 WebP 等更小格式并替换引用、按实际显示尺寸缩图、降低图片运行时内存和显存占用（如降低纹理分辨率、采用目标平台支持的 GPU 压缩纹理格式、按需调整 mipmap）、清理经核实确实未使用的资源、音频降码率、构建配置设纹理压缩预设。图片内存优化也是有效的优化方式，但 WebP 等文件压缩不代表解码后的内存同步下降；分别实测包体与内存收益，保留必要画质和平台兼容性，内存下降不能替代包体达标。目标是用户之后手动从编辑器或一键脚本构建也直接达标。
- 只对 `build/` 产物做后处理（node 脚本转 WebP、去重内联库）而源工程未改，属于兜底，不算完成优化；若必须依赖后处理，要接进用户的一键 bat 或 Cocos 构建钩子，不得交付需要用户额外记住手动运行的脚本。重复内联的公共库（如多份 jszip）在 SuperHTML 或构建配置层面修根因。
- 交付时注明每项优化落在源工程、构建配置还是后处理，并报告三个数字：源资源图片总字节数、`build/web-mobile` 原始产物字节数、最终 Google 产物字节数。前两个没变小就是没落到源头。
- "重新构建"指实际执行 Cocos Creator 命令行构建（`CocosCreator.exe --project <项目> --build "configPath=<配置>"`，3.8 成功退出码 36）或从头跑用户的一键脚本，并核对产物 mtime 晚于本次构建开始时间；对旧 `build/` 直接跑后处理不算。交付时给出构建命令、退出码、产物时间戳。
- 优化完成后删除或移走旧 `build/`，按用户平时的手动方式干净构建一次并测量，以此作为验收依据，不用中间产物代替。

## 运行与商店跳转验收

- 体积达标后才进入正式运行验收（定位压缩导致的问题可做必要运行诊断）。实际运行入口 HTML 并进入关卡或可交互的游戏内容；合理启动期后仍黑屏、停在插屏、进不了游戏即失败。后续修复改变 Google 产物时重新测体积。
- 每个渠道分别运行最终 HTML（ZIP 先解压）做一次简洁的商店跳转验证，不以一个渠道代表其他渠道。先定位工程里的跳转按钮或商店逻辑，在成品中点击该按钮（不便点击时调用同一游戏入口），确认完整调用链进入当前渠道的跳转接口并指向配置的商店或由渠道 SDK 接管；不能只查链接字符串或绕过游戏逻辑直接调 SDK。
- 按实际渠道接口验证（如 AppLovin 的 MRAID），浏览器 `window.open` 成功不算通过。有渠道测试环境时用测试环境；没有时在本地模拟该渠道 SDK，记录成品实际发出的调用、参数和目标，调用链正确且目标指向配置的商店即为"接口模拟通过"。模拟通过允许交付，交付时逐渠道标注"接口模拟通过，平台实机未验证"，平台实机验证由用户在渠道后台完成；只有调用链断裂、接口或目标错误才算失败。
- 简要记录各渠道触发入口、调用接口、目标、结果。发现失效先修复并重新生成受影响成品再针对性复验，不扩大为全量测试。

## 交付门槛

- 本次要求的所有渠道产物全部通过体积、运行、跳转验收才允许交付；任一项失败即不允许交付，不能以"已生成文件""构建成功""部分渠道通过"代替。验收证据必须对应最终交付版本，未通过前不得上传交付位置或宣称完成。
- "不允许交付"意味着继续修复：在授权范围内自行定位、选方案、执行、复验，按"体积 → 运行 → 跳转 → 交付"推进，不把可自行解决的问题转交用户。
- 未验证、结果无法确认都不算通过；先主动解决可修复的环境问题或用等效途径验证。渠道真实测试环境缺失不构成阻塞，按「运行与商店跳转验收」的 SDK 模拟完成验证即可。普通构建失败、超限、跳转故障、一次工具失败都不是停止理由；只有缺少必需的外部权限、资料或环境时，才说明具体阻塞证据并请求最小协助，任务保持未完成。用户明确要求跳过验证时，以当前指令为准，可以交付已生成的产物并标明未验证项目，不宣称验收通过。
