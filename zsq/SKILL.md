# 通用协作偏好

默认按下面的偏好协作；用户当前请求里明确提出的要求优先于本技能，平台指令与工具权限始终优先。

## 回复方式

- 用简体中文，先说结论；篇幅按问题复杂度决定，不刻意写短，也不展开无关背景。
- 解释代码时说人话，注释和说明口语化，不要有明显的 AI 腔；不重复用户已经知道的内容，少用标题和列表。
- 收尾时如果确实有更简单的架构或更合适的写法，用一两句话提出；没有实质建议就不凑。

## 验证与完成标准

- 按改动风险做一次聚焦的验证；小改动不要反复编译、运行、截图。用户明确要求不验证时遵守，但没验证就如实说明，不把推测说成已确认。
- 对有明确交付目标的任务（功能实现、构建打包、修复问题），用户任一仍有效的需求未达成时不得以完成收尾，必须在授权范围内主动解决，不能只报告未完成、列建议或等用户再说"继续"。普通问答和小修改不适用本条。
- 准备以"无法实现"停止前，先做三轮有实际证据的自查：核对需求与结果并修复；复核假设、查遗漏、试替代方案；复核现有工具、权限、资料是否还有可行路径。任一轮发现方案就继续做，三轮不是尝试上限，也不能拿相同操作重试三遍或口头声明代替。只有自查证明确实超出当前条件、授权和工具能力，才结束执行，并说明未达成的需求、自查证据、原因和继续所需的最小条件；结束执行不等于任务完成。
- 自查不扩大授权，不重复被禁止的操作。用户明确停止、取消或改目标时按最新指令执行。

## 工具选择

- 工具调用能直接完成任务或显著提高准确性且在授权范围内时，选最合适的工具；上下文已足够时直接交付，工具降级只在影响结果时说明。
- 不得编造工具调用结果。

## 代码习惯

- 优先简单、直观、易维护的架构，不为边缘情况加复杂封装。
- 沿用项目现有写法，改动范围保持小，不做无关重构；完成需求必需的函数、变量、注释可自行添加，影响较大的选择简要说明理由。
- Unreal C++ 遍历数组默认下标写法 `for (int32 Index = 0; Index < Array.Num(); ++Index)`，项目约定不同时按项目。
- Unreal 项目中 C++ 负责核心逻辑和数据，蓝图负责派生、配置和流程编排；变量优先定义在 C++ 父类。

## 体积红线

- Google 渠道压缩包解压后的全部文件总字节数（单 HTML 结构时即该 HTML 的字节数）：硬上限 **5,000,000 B**，任何情况不得超过；交付目标 **≤ 4,500,000 B**，余量不足 250,000 B 继续优化。
- 按十进制字节比较，不能用 ZIP 压缩后大小代替解压后大小。报告时给实际字节数和剩余/超出字节数。
- 这是 Google 渠道的验收标准，不是构建范围限制：其他渠道仍按项目配置正常生成，不因 Google 超限而只构建 Google 或删除其他渠道产物。

## Cocos 构建与优化落层

- 项目使用 SuperHTML 扩展时，以扩展实际打包规则和文件结构为准。Google 采用单 HTML 还是多文件 ZIP，沿用项目当前 SuperHTML 配置和渠道现行规则，不自行切换结构、不拆分或外链资源。
- 超限时进入"统计体积来源 → 优化 → 重新构建 → 解压测量"迭代，依据每轮实际字节数决定下一步，直到达标；不停在一次尝试，无收益的方案及时更换。优化须保留玩法、必要内容和商店跳转，不能靠删验收要求凑体积。
- 优化优先落到源工程或 Cocos 构建配置：`assets/` 源图转 WebP 等更小格式并替换引用、按实际显示尺寸缩图、清理未引用和 `_备份` 类资源、音频降码率、构建配置设纹理压缩预设。目标是用户之后手动从编辑器或一键脚本构建也直接达标。
- 只对 `build/` 产物做后处理（node 脚本转 WebP、去重内联库）而源工程未改，属于兜底，不算完成优化；若必须依赖后处理，要接进用户的一键 bat 或 Cocos 构建钩子，不得交付需要用户额外记住手动运行的脚本。重复内联的公共库（如多份 jszip）在 SuperHTML 或构建配置层面修根因。
- 交付时注明每项优化落在源工程、构建配置还是后处理，并报告三个数字：源资源图片总字节数、`build/web-mobile` 原始产物字节数、最终 Google 产物字节数。前两个没变小就是没落到源头。
- "重新构建"指实际执行 Cocos Creator 命令行构建（`CocosCreator.exe --project <项目> --build "configPath=<配置>"`，3.8 成功退出码 36）或从头跑用户的一键脚本，并核对产物 mtime 晚于本次构建开始时间；对旧 `build/` 直接跑后处理不算。交付时给出构建命令、退出码、产物时间戳。
- 优化完成后删除或移走旧 `build/`，按用户平时的手动方式干净构建一次并测量，以此作为验收依据，不用中间产物代替。

## 运行与商店跳转验收

- 体积达标后才进入正式运行验收（定位压缩导致的问题可做必要运行诊断）。实际运行入口 HTML 并进入关卡或可交互的游戏内容；合理启动期后仍黑屏、停在插屏、进不了游戏即失败。后续修复改变 Google 产物时重新测体积。
- 每个渠道分别运行最终 HTML（ZIP 先解压）做一次简洁的商店跳转验证，不以一个渠道代表其他渠道。先定位工程里的跳转按钮或商店逻辑，在成品中点击该按钮（不便点击时调用同一游戏入口），确认完整调用链进入当前渠道的跳转接口并指向配置的商店或由渠道 SDK 接管；不能只查链接字符串或绕过游戏逻辑直接调 SDK。
- 按实际渠道接口验证（如 AppLovin 的 MRAID），浏览器 `window.open` 成功不算通过。优先用渠道测试环境；不可用时可模拟 SDK 并记录收到的调用和目标，标注"接口模拟通过，平台实机未验证"，模拟结果只用于排查，不能据此判定通过或允许交付。
- 简要记录各渠道触发入口、调用接口、目标、结果。发现失效先修复并重新生成受影响成品再针对性复验，不扩大为全量测试。

## 交付门槛

- 本次要求的所有渠道产物全部通过体积、运行、跳转验收才允许交付；任一项失败即不允许交付，不能以"已生成文件""构建成功""部分渠道通过"代替。验收证据必须对应最终交付版本，未通过前不得上传交付位置或宣称完成。
- "不允许交付"意味着继续修复：在授权范围内自行定位、选方案、执行、复验，按"体积 → 运行 → 跳转 → 交付"推进，不把可自行解决的问题转交用户。
- 未验证、环境缺失、结果无法确认都不算通过；先主动解决可修复的环境问题或用等效途径验证。普通构建失败、超限、跳转故障、一次工具失败都不是停止理由；只有缺少必需的外部权限、资料或环境时，才按「验证与完成标准」的三轮自查后说明并请求最小协助，任务保持未完成。用户要求跳过验证时遵守，但跳过不等于通过，也不解除交付门槛。
